# Eternal → Hermes design-intelligence pipeline

The Eternal game generates **design intelligence**: records of human design
choices, comparative ratings, and outcomes. This directory is the contract
between the game and the agent.

```
eternal/
├── design-intelligence/
│   ├── signals/       ← the game drops JSONL exports here (raw)
│   ├── principles/    ← distilled principles, one markdown file each (curated)
│   └── digest.md      ← generated by ingest.py — what the agent reads first
└── ingest.py          ← validates signals, refreshes digest, emits training tasks
```

At deploy time this whole directory is available to the agent read-only at
`$HERMES_HOME/eternal`.

## Signal schema (v0)

One JSON object per line in `signals/*.jsonl`. Required fields:

```json
{
  "id": "unique-signal-id",
  "type": "choice | rating | outcome",
  "task": "poster | logo | layout | palette | type-pairing | ...",
  "summary": "one sentence: what was chosen/rated and the result"
}
```

Optional fields (free-form, preserved verbatim): `ts`, `context`, `design`,
`verdict`, `score` (number), `players` (int). Unknown fields are kept — the
schema is additive; `ingest.py` only enforces the four required keys.

## Principles

`principles/<slug>.md` — one principle per file, written by humans or by the
agent after digesting signals. Keep them operational (a rule you can check
against a composition, not an essay). The slug is the citation handle the agent
uses, e.g. `principles/contrast-01.md` → cited as `eternal:contrast-01`.

## Ingestion

```bash
python3 eternal/ingest.py            # validate + digest + emit training tasks
python3 eternal/ingest.py --check    # validate only (CI-friendly, non-zero on bad lines)
```

Outputs:
- `design-intelligence/digest.md` — corpus summary + recent signals, the file
  the agent's skill and SOUL.md point to.
- `../training/tasks/eternal-design-tasks.jsonl` — one `{"prompt": ...}` per
  usable signal, for `training/run-design-datagen.sh`.
